## Existing architecture and observations

The existing architecture is suitable for extension: independent discovery, metadata and metrics provider interfaces; paced requests with retry/backoff; partial batch/page failure handling; SQLite WAL; process locking; server-side collection; shared pandas analytics; Streamlit; rule-based reports. On this VPS the httpx wrapper uses a standard-library HTTPS transport because native httpcore calls stalled. The latest corrected run completed successfully.

Collected observations:

- Universe/root place IDs, game/creator names and creator ID, description, API creation/update timestamps, first/last observed timestamps, latest raw metadata.
- CCU, cumulative visits, favorites, up/down votes and derived like ratio when available.
- Discovery list IDs and ranks, observation timestamps, Trending/Top Playing snapshot ranks and title/update history.
- Collection summaries and returned location/device context (`all` / `computer`).

Not collected: verified public launch date, competitor revenue, sales, unique players, retention, payer conversion, marketing spend, production budget or studio team size. Description/raw genre metadata is current-state metadata, not a full version history. Revenue cannot be inferred as an observed fact from CCU.

Working analytics include 1h/6h/24h/72h/7d clock-time changes; 24h/72h/7d observed-window averages/peaks with coverage requirements; visits/favorites changes; Trending rank changes; matched-tracked-cohort player-share changes; age filters; a configurable heuristic breakout score; basic threshold events at 1k/5k/10k/50k. Longer horizons currently return insufficient history. No 30d comparison, cohort outcomes, time-to-milestone, growth-duration/decline episodes or Market Opportunities page exists.

## Discovery and cohort readiness

Discovery paginates Roblox's public, undocumented Explore lists, including Trending, Up-and-Coming and genre lists. It admits up to 400 unique candidates per cycle, balanced by list rank, and refreshes every previously tracked unarchived game. This lifetime tracked set can grow above 400. New discovery is supported, but there is no creation-age quota, independent low-visibility launch feed, persistent manual watchlist workflow or per-source discovery coverage ledger.

These are nested rolling age windows, not disjoint launch cohorts. Missing creation dates: 0. Creation is not proof of public release; first observation is not public release either. Current fields do not represent a verified public launch date or its evidence/source.

The sample is selected through visibility/popularity lists and has delayed entry. Unseen games, especially low-CCU or unsuccessful launches, are absent. ## Gaps and correctness issues to address

1. No scheduled off-server backup, retention policy, restore test or backup freshness indicator. Persistent storage is not a backup guarantee.
2. Too little history and insufficient early discovery. No games in the 7d age cohort and none of the 30d/90d sample observed within 24h of creation.
3. Missing launch evidence and censoring/status fields: unknown launch, baseline already above threshold, insufficient follow-up, data gaps and unavailable games need distinct states. A failed API fetch must never imply zero CCU or game failure.
4. Threshold logic has a future recrossing edge case: a game initially above a threshold can later fall below and recross, and the current function can label that later event as its first observed upward crossing. Baseline achievement and subsequent recrossings should be separate event types.
5. Collection-run rows are keyed by UTC hour; retries overwrite the previous summary. Per-attempt provenance, failures and coverage are not fully retained in that table. Snapshots remain deduplicated, but a retry is not a new hourly measurement.
6. Every game's cohort follow-up differs. Observation-age eligibility and missingness denominators are required before comparing milestone rates. Snapshot timestamps vary within each UTC hour and cohorts should show actual matched baseline times.
7. Classification fields exist but all primary/secondary genre, loop, theme and trend-family fields are empty. Raw official first-level genres exist for 450/453 games, with 3 unknown; official genre is not a verified gameplay-loop classification.
8. No niche-level classification coverage, concentration or saturation analysis; no evidence connecting competitors' CCU to the studio's monthly revenue target.

## Five prioritized improvements

Effort below is a planning estimate, not a delivery guarantee. A development day is approximately one focused engineer day; external credentials/source availability can extend elapsed time.

| Priority | Improvement | Impact | Estimated effort |
|---|---|---|---|
| 1 | Verified daily off-server backups and collection/backup health | Protects all accumulated evidence | 0.5–1 day after destination/access are available |
| 2 | New-game admission strategy plus discovery provenance/coverage | Improves evidence about emerging games and reduces mature-list dominance | 1–2 days; external feed verification extra |
| 3 | Creation/observation/verified-launch cohorts and milestone outcomes | Directly answers time-to-traction, sustained outcomes and decline questions | 2–3 days |
| 4 | 30d comparisons and explicit sustained-growth/drawdown episodes | Separates durable opportunities from spikes | 1–2 days plus actual history accumulation |

## Implementation plan — extend, do not rewrite

### Phase 1: Protect and measure the foundation

- Keep the database, providers and systemd deployment. Add a small versioned/additive migration mechanism and test upgrades against a copy of production.
- Use SQLite's online backup API, checksum each backup, send it to separately administered off-server storage, retain e.g. 7 daily + 4 weekly copies and restore-test into a disposable database. Verify integrity and expected tables/counts. Choose an existing remote storage destination before claiming this requirement complete; a second directory on this VPS is insufficient.
- Add backup manifests/freshness and independent collection-attempt records. Record per-source success, response/discovered counts, admitted/skipped counts, paging limits, profile and errors. Keep existing per-game/hour uniqueness.

### Phase 2: Improve admission without losing the tail

- Preserve every tracked game unless explicitly archived. Keep per-game observation/availability status and reasoned missing-data states.
- Reserve configurable discovery budgets for young candidates, Up-and-Coming and source diversity; log the denominator and selection reason. Candidate creation dates must be fetched before age-based admission.
- Add an auditable manual watchlist for small/experimental games and prospective game concepts. Verify any additional public feeds or creator-submitted sources before integrating them through the existing DiscoveryProvider boundary. Do not promise an exhaustive all-launch feed.
- Show a coverage panel: list/profile/page coverage, candidates versus admitted, age/CCU distributions, tracking gaps and classification completeness. Label coverage within the observed discovery sources, never all Roblox launches.

### Phase 3: Cohort and event layer

- Preserve API `created_at` and immutable `first_seen_at`. Add nullable `public_launch_at`, evidence URL/source, verification status and recorded-at timestamp. Keep public launch unknown without verifiable evidence. First observed public accessibility can be stored separately as an observation bound, not an exact retrospective launch date.
- Show rolling creation-age windows 7/30/90d and separate creation-week/first-observed-week cohorts. Only show verified-launch cohorts for evidence-backed launch dates.
- Add persisted/recomputable milestone events at 100/500/1k/5k/10k. Separate baseline already-above, first observed crossing and later recrossings. Store bounding observations and elapsed time from first observation; use observed intervals, not invented exact event times.
- Report eligible counts, unknown counts, baseline-censored counts and follow-up duration. Compare outcomes at equal observation ages (e.g. 24h/7d/30d). Games not yet observed long enough remain right-censored, not failures. Do not initially publish population launch success probabilities.

### Phase 4: Durability and 30d trends

- Extend the current horizon configuration and matched-history logic to 30d. Keep missing history explicit; do not simulate past observations.
- Define configurable persistence rules (e.g. at/above threshold at least 18 of 24 scheduled observations, with an adequate coverage requirement), consecutive/rolling positive growth, peak-to-current drawdown and sustained post-milestone decline. Report sampling gaps and avoid crossing them as if uninterrupted.
- Test zero baselines, missing hours, late admission, baseline achievement, recrossings, restricted/unavailable games, and old/new cohort follow-up asymmetry. Prefer descriptive comparisons before adding survival-model estimates.

### Phase 5: Decision-facing page and reports

- Reuse existing nullable classification fields. Add classification provenance, confidence, taxonomy version and history; start with official genre provenance plus manual loop/theme/family tags. Keep unclassified games visible. Do not guess tags from titles silently.
- Add Market Opportunities using matched tracked cohorts: classified niche size, growth breadth and median growth, new observed entrants, milestone speed/durability, top-5 CCU share and HHI concentration. Include sample sizes, history eligibility and classification coverage.
- Label concentration as within the tracked/classified sample. Label potential saturation as an exploratory competition proxy, not proof of unmet demand, whole-market saturation or expected profit. Flag weak evidence rather than generating an authoritative opportunity score.
- Extend existing daily/weekly Markdown generation with incremental entrants, milestone transitions, sustained movers, drawdowns, niche signals and explicit gaps. Mark partial-day and immature-week windows. Retain report as-of times to avoid confusing rewrites with new events.
- Keep observed metrics separate from heuristic scores and any future user-configured revenue scenario. Competitor revenue is unknown; the $1k–$2k goal requires validating the studio's own retention, conversion, revenue per player and acquisition costs after prototypes are published.

## Acceptance criteria

No existing history is lost; migrations and rollback are tested on copies; backups are demonstrably off-server and restorable; previously tracked disappearing games remain eligible for observation; all requested thresholds and horizons have tests; cohort denominators and censoring are visible; launch dates require evidence; no synthetic history or implicit CCU-to-revenue estimate; production collection and the current dashboard continue working during the rollout.
